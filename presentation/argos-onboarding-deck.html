ARGOS · Joining brief

One operator.
Many robots.

Adaptive Robotic Group Operator System. The supervision layer above any single platform. Terra is the first ground robot, not the whole project.

Welcome them. ARGOS is the architecture for one person supervising a fleet. It is not a ground-robot project, a drone project, or a phone app. Terra is the first physical platform. The thesis starts with a homogeneous Terra fleet. The architecture must not assume wheels, a ground plane, or differential drive for every later robot.

The problem

Continuous control does not scale.

Per robot

Driving or watching each vehicle spends the operator on one chassis. The fleet waits.

Per stream

RGB, depth, clouds, maps, and diagnostics from every robot will not fit the radio or the person.

Per platform

A stack that assumes wheels and a ground plane cannot supervise the next vehicle.

Name the limit: human attention, not CPU count and not the radio by itself. Twenty robots streaming everything is both a bandwidth problem and a cognitive one. Platform-agnostic is a design rule. Do not let a new contributor special-case differential drive into the supervision layer.

ARGOS research problem

Read it slowly. The working form is: what minimum local autonomy lets one operator supervise more robots? Autonomy is the variable. We are not trying to make every robot as autonomous as possible. Parallel tracks exist — monocular depth, communication, sim-to-real, mixed fleets — and they are not all required for the December experiment.

Where this goes

From a single vehicle to the mission.

The job today

Drive robot #4.

The person is the controller. Every obstacle is a driving task, and the rest of the fleet is unattended.

The job ARGOS is for

Make the mission succeed.

The person states the objective. ARGOS matches a ground rover, an aircraft, or a later platform to the work.

Use the example mission: survey this area, identify obstacles, and report regions that need a closer look. A Terra is useful up close. An aerial robot is useful for a fast look. Capability matching is the long-term system. It is not the December deliverable. December is still a homogeneous Terra fleet in simulation.

Autonomy is a variable

December uses L0 to L3.

L0

Teleoperation

The person drives. The robot reports state.

L1

Waypoints

The robot drives to a point. The person clears obstacles.

L2

Stop and ask

The robot stops when the situation is unsafe, and waits.

L3

Local autonomy

The robot avoids locally. The person handles planner failure.

L4 replans a route and finishes the mission. The person handles unusual exceptions. L5 coordinates tasks across robots. The person supervises the objective. Do not skip to L4. The point of L0 through L3 is a measurable difference in how often the robot consumes the operator. Stop-and-ask is a real condition, not a stub on the way to avoidance.

The study

Fleet size crossed with autonomy.

Proposed N

1, 2, 4, 8, 16

How many robots one person is asked to supervise. These sizes are candidate conditions, not a locked protocol and not a result.

Proposed A

L0 to L3

How much each robot can do alone. Record interventions, wait time, completion, idle time, collisions, failures, bandwidth, and workload.

Say proposed, not measured. The architecture note lists N as 1, 2, 4, 8, and 16, and treats that set as a candidate, not a finished study design. Metrics to instrument: human interventions, operator response time, mission completion and duration, robot idle time, collision rate, navigation failures, communication bandwidth, and operator workload. No number on this slide is an outcome.

Who is first

Several robots can ask at once. Severity, mission weight, and whether the robot can safely wait decide the queue.

Always on

Identity, platform, pose, velocity, mission, health, autonomy, and attention. That is the continuous picture.

On request

Camera, depth, occupancy, cloud, trajectory, and planner state move only when a robot asks or the operator selects it.

Give the concrete ordering. A Terra that has lost localization, with an unknown safe state, outranks a Terra that has already stopped at an obstacle. The station has to answer four things: what the fleet is doing, which robots need the person, why, and what action exists. A 3D or VR station is later. Quest 3 is not the first interface.

Capabilities

ARGOS sees waypoint navigation, obstacle detection, and local mapping. Wheel radius and PWM stay in the Terra crates.

Onboard order for Terra is sensors, perception, localization, local map, navigation, planning, control, then the differential-drive rover. argos-core types are RobotId, PlatformType, AutonomyLevel, AttentionState, Capability, HealthStatus. terra-core types are Pose2D, RoverState, Velocity2D, WheelVelocity, RoverDimensions. How the stack stays coherent

Keep the stack boring on purpose.

One job each

A crate has one responsibility. Geometry comes from a mature math library. Interfaces are named and documented.

Match the question

2D sim for navigation. A physics sim when slip matters. A visual sim when the question is the camera.

PID before LQR

DWA is the local planner. Wheel-velocity PID comes first. LQR waits for a failure PID cannot fix.

terra-sim needs pose, heading, velocity, goals, obstacles, collision, and time. The model is x-dot = v cos theta, y-dot = v sin theta, theta-dot = omega. MuJoCo is for friction, slip, inertia, motors, and slopes. Unreal is for monocular RGB, lighting, and camera placement. DWA samples v and omega, rejects collisions, and scores heading, clearance, and forward progress. A-star, later, answers where to go. DWA answers how to move safely now. Inside the code, use meters, seconds, and radians. Convert at the hardware and UI boundary.

What we expect

Leave a test, a log, and a boundary.

An interface

Plan from state, map, and goal. Not a long list of loose numbers. Someone else has to call it.

Evidence

Tests for distance, projection, and rejected collisions. Logs with a time and a robot id. A config that can be rerun.

Restraint

No new SLAM, physics engine, VR shell, or custom network stack unless this architecture cannot do the job.

A change should carry the implementation, the tests, the note, and the config. Example tests: waypoint distance, a center depth pixel projects forward, DWA rejects a colliding trajectory, a Terra reaches a clear goal. Log mission start and completion, collision, attention requested and received, intervention, planner failure, localization failure, stop, and resume. A rerun record names fleet size, autonomy level, environment, and seed. Keep reviews small. Do not rewrite mapping, networking, and coordinate frames in one branch. Gaussian splatting, LQR, and a custom protocol need a written reason.

December defense

Four milestones. Then stop adding features.

01

One Terra

A simulated rover reaches a goal, then handles an obstacle.

02

A fleet

Several Terras run independent missions and share one protocol.

03

A station

The operator sees fleet state and an attention queue.

04

Freeze

Collect data, analyze it, write, and validate. Features wait.

The critical chain is simulation, waypoint navigation, obstacle detection, stop-and-ask, DWA, multi-Terra simulation, the station, attention requests, then the supervision experiment. Milestone one is goal, then obstacle, then local avoidance. After the system can run the study, engineering yields to data collection, analysis, writing, and validation. Extra work is welcome only when it does not put that chain at risk.
